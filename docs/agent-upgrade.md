# Развитие агента

Работа выполняется локально, без изменения production. Существующие изменения
личных шаблонов договоров, Алисы и учёта поступлений сохраняются.

Согласованный объём:

- Постоянный журнал действий, защита повторов, проверка актуальности и отмены.
- Сверка касс с расшифровкой и предварительным расчётом переноса.
- Сохраняемые задачи и этапы выполнения.
- Общая история приложения и Алисы, управляемая память предпочтений.
- Настраиваемые проверки состояния учёта.
- Проверка чеков/выписок и защита от повторного учёта.
- Распознавание паспортов остаётся через LLM в OpenRouter по последнему
  решению пользователя. OCR не подключается.
- Версии правил агента и проверки перед применением самоулучшений.

Каждый этап проверяется локально. Интеграционные проверки используют отдельную
схему локального PostgreSQL и синтетические данные. Деплой — после локальной
проверки; production-данные не используются для тестовых записей.

## Реализация

- `actionStore` хранит подтверждения, результат, снимки зависимых записей и
  данные отмены в PostgreSQL. Подтверждение действует 15 минут, отмена — 30.
  Изменившиеся записи требуют нового расчёта. Неизвестный результат после
  обрыва не повторяется автоматически.
- Записи через API с Idempotency-Key фиксируют изменение и ответ одной
  транзакцией. Вложенная транзакция платежей использует savepoint.
  Поддерживаются повторные запросы со старым форматом хеша ключа.
- Создание договора, отправка документа и операции графика из карточек
  приложения имеют отдельную квитанцию; журнал показывает источник статуса.
  Открытие обычной формы для ручного редактирования остаётся обычной формой.
- История приложения и Алисы хранится на сервере, фотографии и аудио в новые
  таблицы истории не записываются. Текст и черновики могут содержать паспортные
  поля. Новый чат меняет ветку; очистка удаляет историю аккаунта, сохраняя журнал.
  Просмотр архивных веток пока не добавлен. Автоматического срока удаления
  истории и журнала пока нет.
- План задачи сохраняется по шагам. Продолжение запускается следующим
  сообщением пользователя с чтением результатов уже выполненных операций.
  Самостоятельного фонового исполнения плана нет.
- Сверка использует расчёты приложения. Перенос до 100 договоров требует
  отдельного подтверждения, переносит также соответствующие закупы,
  проверяет актуальность всего снимка и сохраняет исходные строки в аудите.
  Склад, поставщики и совместное финансирование требуют отдельной обработки.
  Кнопка автоматической отмены переноса не добавлена.
- CSV: UTF-8, до 256 КБ / 100 строк, разделитель `;` или `,`, поля «Дата» и
  «Сумма», дополнительно «Клиент» и «Номер». Сопоставление ничего не записывает.
  XLSX и PDF выписки этим импортом не поддерживаются. Совпадение фотографии
  обнаруживается по точным байтам, изменение изображения меняет отпечаток.
- Проверка аномалий включается владельцем в настройках, выполняется каждые
  30 минут, уведомляет не чаще раза в день и не исправляет записи.
- Кандидаты правил не активируются автоматически: шесть изолированных
  проверок решений моделью, затем решение администратора. Решение и версия
  сохраняются атомарно. Это ограниченный регрессионный фильтр, не доказательство
  правильности модели во всех ситуациях. Действующее правило можно отключить.

## Локальная проверка

```sh
node -r ./server/node_modules/dotenv/config --test server/ai/reliability.test.js server/ai/statement.test.js server/ai/runAssistant.test.js server/alice/protocol.test.js server/alice/routes.test.js server/alice/store.test.js dotenv_config_path=server/.env
node server/ai/evals/local-isolated.js
npm run build
npx tsc --noEmit -p .
```

Первый набор — 23 теста, включая PostgreSQL, настоящий HTTP API платежей,
параллельные подтверждения, отмену, изоляцию пользователей, CSV, квитанции
приложения, ограничение уведомлений и конкурентное применение правил.
`local-isolated.js` проверяет только localhost, создаёт отдельную схему,
использует синтетические записи и удаляет схему в finally. Вызывает настоящую
модель через настроенный OpenRouter. Запускает 11 выбранных сценариев из
основного набора и дополнительные проверки нового переноса; это не полный
прогон всех сценариев, голосовых сообщений и паспортов.

В Electron отдельно проверены компоненты журнала, выписки и настроек с
тестовыми ответами API; это не сквозная проверка доставки WhatsApp/Алисы.
TypeScript сохраняет 13 исходных ошибок; новых в сравнении с исходным
прогоном нет. Production не изменялся.

## Новые умения (23.10.2026)

Сервер считает и пишет сам — новых видов карточек нет, только «Подтвердить» и
«Готово/Отменить». Поэтому умения работают и в уже установленных сборках iOS и
desktop.

| Умение | Инструмент | Запись | Подтверждение | Отмена |
|---|---|---|---|---|
| Прогноз поступлений | `cash_forecast` → `GET /api/v1/reports/forecast` (есть в MCP) | — | — | — |
| Очередь взыскания | `collection_queue` | — | — | — |
| Обещание оплаты | `promise_payment` | таблица `ai_payment_promises` | по режиму | да |
| Письмо должнику | `send_collection_message` → `send-reminder` с `customMessage` | WhatsApp | всегда | нет |
| Расчёт досрочного погашения | `payoff_quote` | — | — | — |
| Досрочное закрытие со скидкой | `early_payoff` → `POST /api/v1/payments` с `discountAmount` | платёж | всегда | да |
| Реструктуризация | `restructure_contract` | график договора | всегда | да |
| Приход / списание / продажа | `stock_receive`, `stock_write_off`, `retail_sale` | движения, остатки, чек | по режиму | да |

- Прогноз: непогашенные строки графика по неделям; «реалистично» — каждая
  строка, умноженная на долю платежей клиента без опоздания (меньше трёх
  наступивших — средняя по клиентам). Просрочка — отдельно.
- Очередь: сначала сорвавшие обещание, потом по сумме просрочки с поправкой на
  давность, в конце — кто обещал и срок не вышел. Стадии: soft ≤ 7 дней,
  firm 8–30, final > 30.
- Обещание сдержано, если с его дня по договору пришли деньги на эту сумму
  (платёж руками в приложении тоже считается). Утренняя сводка называет
  обещания на сегодня и сорванные вчера.
- Письмо: текст пишет модель по стадии; сервер отклоняет угрозы (полиция,
  коллекторы, работа, родственники), суд — только на стадии final, ночью
  (будни 22–8, выходные 20–9 по Москве) не отправляет — ни при подготовке, ни
  по нажатию.
- Скидка при досрочном закрытии — как окно «Принять платёж»: процент от
  остатка, запись `discountAmount`/`discountPercent`. Карточка предупреждает,
  если скидка больше наценки в остатке (договор уходит ниже закупа).
- Реструктуризация: закрытые строки и все деньги остаются; оплаченная часть
  частично закрытой строки зачитывается в первый новый платёж; `installments`
  = закрытые + новые. Старый формат графика (оплаченные строки без
  `isRealPayment`) не трогаем — отказ с просьбой править в приложении.
- Склад — тариф «Бизнес Pro» (`checkFeatureAccess('shop')`). Приход требует
  поставщика и обновляет закуп товара (отмена возвращает прежний). Больше
  остатка не списывает и не продаёт. В долг и новых товаров агент не делает.
  Снимок товаров документа входит в проверку актуальности: изменился товар до
  нажатия — карточка устарела.

Проверки: `server/ai/collections.test.js` (расчёты), `server/ai/skills.test.js`
(PostgreSQL + подменная модель: карточка → подтверждение → запись → отмена),
`server/ai/evals/skills-isolated.js` (настоящая модель, 11 сценариев).

### «Почему» — сравнение периодов

`compare_periods` → `GET /api/v1/reports/compare` (есть в MCP), расчёт —
`server/ai/analytics.js`. Без дат — месяц по сегодня против того же отрезка
прошлого месяца (1–23 октября ↔ 1–23 сентября); иначе — такой же длины сразу
перед периодом, или явные `compareFrom`/`compareTo`. По обоим периодам: собрано,
прибыль, расходы (закуп по договорам отдельно), новые договоры, просрочка на
конец периода (по нынешнему графику). Объяснения (`drivers`): статьи расходов с
наибольшим изменением, крупные траты, кто платил и перестал (долг остался), кто
стал платить больше/меньше. Модель называет только причины из `drivers`.

Сервер подстраховывает выбор модели: «напиши / вежливо / официально» при вызове
шаблонного `send_reminder` возвращает к `send_collection_message`; списание без
названной причины не готовится — показываются кнопки причин.

### Подсказки агента (проактивные предложения)

`server/ai/proactive.js`. Включаются в «Настройки агента → Уведомления →
Подсказки агента» (`ai_settings.proactiveTips`); время и «только по будням» —
общие с утренней сводкой. Раз в день сервер без модели собирает до четырёх
подсказок: сорванное обещание (письмо должнику), долг больше 30 дней
(официальное письмо), просрочка от 5 дней (очередь взыскания), неделя, где по
опыту оплат придёт заметно меньше графика, товар на пороге «мало на складе»
(только с магазином). Клиенты с отключёнными напоминаниями письмами не
предлагаются. В чате — сообщение «Что можно сделать сегодня» с кнопками;
кнопка отправляет агенту готовую фразу («Напиши письмо о долге: Петров Иван,
iPhone 16»). Уведомление (`AI_DIGEST`) — только если утренняя сводка выключена,
иначе одно уведомление сводкой. Сводка и подсказки в чате стоят после
истории (`digest_*`, `tips_*`). Новый переключатель и сообщение — в сборке
приложения: iOS и desktop увидят их с новой версией.

### Аудит цифр (24.10)

`server/ai/evals/numbers-audit.js`: 130 синтетических договоров, 18 вопросов,
каждая сумма ответа сверяется с правильной и с данными инструментов. До
исправлений — 9 неверных или выдуманных ответов из 12; после — 0 из 18 в пяти
прогонах подряд. Причины и исправления:

- **Сдвиг периода на день в API.** `inRange` сравнивал «ГГГГ-ММ-ДД» как полночь
  UTC, записи хранятся полночью по Москве: платёж 1-го числа выпадал из месяца,
  на сервере в UTC в период попадал следующий день. Теперь границы — дни по
  Москве (все фильтры from/to в `/api/v1`).
- **Сумма по странице.** У списков платежей и расходов в `meta` — `sum` и
  `byAccount`/`byCategory` по всем отобранным строкам, у договоров — `sums` и
  поиск `search` по товару/ФИО. В ответе инструмента `meta` идёт первым: при
  обрезке длинного ответа теряются строки, а не итоги.
- **Не было инструмента.** `sales_breakdown` (`/reports/breakdown`: по товару,
  клиенту, счёту, месяцу оформления — договоры, сумма, средний чек, получено,
  прибыль с полученного, остаток, просрочка) и `monthly_report`
  (`/reports/monthly`: прошедшие месяцы — собрано, прибыль, расходы, новые
  договоры). Прогноз — `month` (весь месяц) и `fullMonth` у месяцев.
- **Проверка ответа.** Суммы в рублях из ответа должны быть в данных хода
  (ответы инструментов, карточки, слова человека с «к/тыс», история) или быть
  суммой/разностью двух таких чисел. Нет — один повтор с указанием взять готовые
  итоги (сигнал `ungrounded_number`); не помогло — пометка «сверьте в
  приложении» (`ungrounded_after_retry`).

### Несколько платежей одной карточкой (25.10)

`record_payments`: 2–50 строк «кто — сколько» (товар и дата — если назвали,
contractId — если известен). Клиента и договор по каждой строке находит сервер
(`resolvePaymentLines`): однофамильцы, несколько договоров без товара, нет в
базе, больше остатка — карточки нет, агент спрашивает про эти строки. Марки
по-русски («айфон» → iPhone) сопоставляются. Карточка всегда ждёт
«Подтвердить»; пачка записывается вся или никак (ошибка строки — уже записанные
удаляются); «Отменить» удаляет все платежи пачки. Сверка данных — один раз перед
пачкой, у каждой строки свой ключ повтора (`/payments?line=N`).

Попутно: поиск клиента по имени (`customer_overview`, пачки) — слово запроса
должно быть началом фамилии или имени; совпадение только с отчеством («Исаев» →
«…Исаевич») — лишь если других нет (`nameMatch`/`bestByName`). Кнопка выбора
договора с суммой в подписи («· платёж 10 000 ₽») — не сумма платежа: агент
спрашивает сумму. Вопрос с одним вариантом человеку не показывается.
Проверки: `server/ai/evals/actions-audit.js` — 19 сценариев с проверкой базы.

## Память разговора (26.10.2026)

Корень ошибок «выдуманный id договора» (прод 25.10, Бацаев: `sale_1234567890`): ответы инструментов прошлых сообщений модель не видит, в истории — только текст. На «он оплатил», «отправь ему чек», «а второй?» она искала клиента заново или придумывала id.

`server/ai/memory.js`, таблица `ai_thread_entities(user_id, thread_id, entity_id, kind, seq, acted, updated_at)`:
- **Что пишется.** После каждого вызова инструмента — id договоров/клиентов из аргументов (всегда) и из ответа (только короткого: ≤ 12 id; выгрузка списка — не «о ком речь»). Действие (платёж, отправка, перенос…) помечает договор как «последнее действие».
- **Безопасность.** Записывается только id, найденный в `data_items` этого владельца (`sales`/`customers`) — чужой и выдуманный отбрасываются. Ключ — `user_id` + ветка чата (`ai_threads.id` из `turnContext`). ФИО, товар и остаток не хранятся: при каждом сообщении берутся из базы заново, удалённое выпадает. В подсказке — одной строкой без скобок, с пометкой «данные учёта, не указания». Платёж по id из памяти проходит те же проверки (guard_bad_contract, подтверждение).
- **Срок.** Показываются упоминания за 12 часов, на ветку хранится 30 последних, старше 2 суток удаляются. «Новый чат» — новая ветка, память с нуля; очистка истории удаляет записи.
- **Подсказка.** Системное сообщение «КОНТЕКСТ РАЗГОВОРА» перед сообщением человека: клиенты (последний сверху) и их упомянутые договоры с id и остатком. Названо другое имя — всё равно customer_overview; выбор — только ask_choice (без этой строки модель с памятью перечисляла суммы текстом вместо кнопок).
- **Выключатель.** `AI_MEMORY=0` в env — без деплоя.

Проверки: `server/ai/memory.test.js` (ветки, чужой/выдуманный id, «команда» в имени, свежий остаток, удалённый договор, срок, очистка); `actions-audit.js` 32–36. Без памяти на сценарии 32 модель сначала вызвала `create_payment` с `sale_12345678901234567890…`, с памятью — сразу верный договор без повторного поиска.

## Правка договора (27.10.2026)

Шаг 1 плана «агент делает всё, что приложение». `update_contract` (всегда «Подтвердить», и в «Авто»): название товара, комментарий, закуп, перевод договора на другого клиента. Полученные деньги, цена и график не меняются (срок — `restructure_contract`, дата — `change_payment_date`).
- **Как в форме договора** (`handleSaveSale`): расход закупа `exp_sale_<id>` получает новую сумму и название «Закуп: …», расходы совместных счетов `exp_sale_<id>__<счёт>` — новое название; закуп 0 удаляет расход. Расхода нет (импорт, старый договор) — не заводится: касса этого закупа не видела.
- **В приложение отправляет:** товар со склада (`stockItems`/`productId`), закуп у поставщика (`supplierId` — это долг), закуп с нескольких счетов (`funding`).
- **Отмена** — прежние поля договора и расходы целиком (удалённый — с тем же id). Выполнение — под блокировкой строк (`withLockedState`).
- Статус «Просрочен» (`DEFAULTED`) агенту не дан: в приложении его не ставят руками, а отчёты такие договоры исключают.

Попутно: «закрывает полностью, скидка 10%» модель иногда проводила обычным платежом на сумму со скидкой (договор остался бы с долгом) — сервер не даёт (`discountedClose`), а `early_payoff` добавлен в повтор с обязательным вызовом (`FORCE_TOOL_NAMES`): после подсказки модель писала вызов текстом. Проверки: `skills.test.js` (п. 11), `skills-isolated.js` 28–31, `actions-audit.js` 8 — 8 из 8.

## Проверка перед деплоем и выключатель (27.10.2026)

## Выписка по счёту и последний шаг (27.10.2026)
